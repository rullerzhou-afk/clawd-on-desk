# Known Limitations

[Back to README](../../README.md)

| Limitation | Details |
|---|---|
| **Codex CLI: terminal focus is best-effort** | `request_user_input` cards can jump back to a local Codex session when its official-hook/session metadata identifies a focus target. JSONL alone may not carry a usable terminal PID, and Remote SSH sessions cannot focus a window on the remote host; in those cases the card remains a read-only reminder. |
| **Codex CLI: partial hook coverage** | Official hooks cover live state and `PermissionRequest` observation/intercept mode, but not every runtime signal. Clawd keeps JSONL polling active for hook-disabled sessions and fallback-only events such as web search, compaction, and aborted turns, so those state/metadata events can still have polling latency. Approval prompts are not inferred from JSONL; they require official `PermissionRequest` hooks. |
| **Codex CLI: user-input cards are read-only** | Codex does not expose `request_user_input` through the official hook event set. Clawd observes the JSONL transcript, so the reminder can arrive after the polling interval. Choices and free-form answers stay in Codex's native UI; Clawd neither injects keystrokes nor mirrors these questions to Telegram/Feishu approval actions. |
| **Copilot CLI: no Telegram remote approval (yet)** | Copilot permission bubbles work locally, but v1 wiring intentionally excludes Telegram remote approval. The `edit` tool's full diff is the worst-case payload and needs a safe summary formatter before it can be sent over the bridge. The local bubble path is unaffected. |
| **Gemini CLI: no permission bubble** | Gemini handles tool approval inside the terminal. Clawd observes Gemini hook events, but does not show permission bubbles unless Gemini adds a compatible blocking approval contract later. |
| **Antigravity CLI: no permission bubble (state-only)** | Clawd does **not** pop any permission bubble for agy. Every Allow / Deny / Always-allow choice happens in agy's own 5-option terminal menu (Yes / Yes Persist / No / Always Deny / Always Deny Persist). For a permanent rule, choose the menu item labeled "Persist to settings.json" in agy's menu — the rule lands in `~/.gemini/antigravity-cli/settings.json` where you can also clear it. Dogfooding showed that adding a Clawd bubble on top produced 8-10 confirmations per single user task, so Clawd intentionally lets agy own permission flow end-to-end. Pet still reflects working / idle / attention state via PreInvocation / PostToolUse / Stop hooks. |
| **Cursor Agent: no permission bubble** | Cursor handles permissions via stdout JSON in the hook, not HTTP blocking — Clawd can't intercept the approval flow. |
| **Cursor Agent: startup recovery** | No process detection on startup (matching the editor PID would false-trigger on any Cursor instance). Clawd stays idle until the first hook event fires. |
| **Custom HTTP agents: state-only, sender required** | Registering an executable assigns an ID and exposes the `/state` contract; it does not install a hook, watch the process, or prove the application is an AI tool. The application or an adapter must send events using the current port from `~/.clawd/runtime.json`. Custom agents cannot use `/permission` in v1, so approval stays in the application's native UI. |
| **Hermes Agent: install required before use** | Hermes is listed in Settings but starts Not installed on fresh installs. Clawd does not write Hermes plugin files until you explicitly install the integration and a real Hermes install is detected. Install Hermes, then use **Settings -> Agents -> Install** or run `npm run install:hermes-plugin`. |
| **Hermes Agent: partial permission bubble support** | Hermes plugin events cover state, sessions, SessionEnd, tool activity, terminal focus, clarify elicitation bubbles, and plugin-originated permission bubbles. Tools explicitly listed in `CLAWD_HERMES_PERMISSION_TOOLS` fail closed when Clawd returns no decision or is unavailable; Hermes currently has no native approval prompt for that opt-in gate, so retry the tool after Clawd can show the bubble. Clawd does not fully replace Hermes' native approval menu yet: `once` / `session` / `always` persistence still belongs to Hermes until upstream exposes a blocking approval-resolution hook. Subagent lifecycle also still needs paired upstream start/stop events. |
| **Kiro CLI: no session tracking** | Kiro CLI stdin JSON has no session_id — all Kiro sessions are merged into a single tracked session. |
| **Kiro CLI: no SessionEnd** | Kiro CLI has no session end event, so Clawd can't detect when a Kiro session ends. |
| **Kiro CLI: no subagent detection** | Kiro CLI has no subagent events, so juggling/conducting animations won't trigger. |
| **Kiro CLI: terminal permission prompts stay in terminal** | Kiro state hooks are verified on macOS and Windows, but when Kiro shows native terminal permission prompts such as `t / y / n`, those still need to be handled in the terminal. Clawd does not currently replace that flow. |
| **Kimi Code CLI (Kimi-CLI): hook-only runtime path** | Kimi in Clawd is hook-only (`~/.kimi/config.toml`). If a future Kimi release breaks hook delivery, recover by reverting to the historical log-poll implementation from commit `e57679a` (the current `agents/kimi-log-monitor.js` is a compatibility stub). |
| **Kimi Code subscription quota is experimental and manual-only** | Kimi's normal login and hooks expose no machine-readable subscription quota. Clawd therefore requires a dedicated Kimi Code API Key and queries the experimental `/coding/v1/usages` endpoint only after an explicit Connect/Replace/Refresh click. It does not poll in the background. The Key can invoke models and consume quota/Extra Usage; Disconnect/Forget do not revoke it in Kimi Console. A generic 403 is kept as an error with last-known data instead of being guessed as 100%, so an exhausted account may not visibly reach a full ring if Kimi blocks the usage endpoint itself. |
| **Kimi Code CLI (Kimi-CLI): `[[hooks]]` blocks referencing `kimi-hook.js` are owned by Clawd** | Clawd auto-syncs Kimi hooks on every startup (and from `npm run install:kimi-hooks`). Any `[[hooks]]` block whose `command` references `kimi-hook.js` is treated as Clawd-owned: all such blocks are removed and rewritten as the canonical 13 events with a `--permission-mode=<mode>` flag on the command (a mode chosen in a prior install — including via the retired `CLAWD_KIMI_PERMISSION_MODE=…` env-prefix form — is carried over when no env var is passed; new installs default to `suspect`). Non-hook sections in `config.toml` (e.g. `[server]`, `[mcp]`, `[[tools]]`) and any `[[hooks]]` block you wrote yourself without referencing `kimi-hook.js` are left untouched. Change permission-mode behavior via env vars (e.g. `CLAWD_KIMI_PERMISSION_MODE`) before re-running the installer instead of hand-editing the `command` field. |
| **Legacy Kimi CLI: suspect heuristic can flash a false-alarm cue** | On legacy `~/.kimi` installs the permission cue defaults to the suspect heuristic (current kimi-cli emits no explicit permission fields, so the old explicit-only default never fired; queued approvals in one message each re-surface their own cue since the batched-approvals fix). The trade-off: a *pre-approved* gated command running longer than ~0.8s briefly shows a cue as if an approval were pending — the card auto-closes after a few seconds, and the pet keeps its notification pose until the tool finishes. Opt out persistently with `CLAWD_KIMI_PERMISSION_MODE=explicit` before re-running the installer, override temporarily with the same env var at kimi-cli runtime, or disable Kimi permission cues entirely in **Settings → Agents**. Also note: with the legacy event vocabulary the *next* queued approval's cue re-arms only after the previous tool's `PostToolUse`, so a long-running first tool delays the second cue (late but correct). |
| **opencode: child sessions are background-only** | When opencode emits `session.created` with `event.properties.info.parentID`, Clawd treats that child/subtask as headless background work owned by the root session. It is hidden from HUD/focus surfaces and does not contribute to multi-session fanout animations. |
| **opencode: terminal focus limited to spawning terminal** | The plugin runs in-process with opencode, so `source_pid` points to the terminal that launched opencode. If you use `opencode attach` from a different window, terminal focus jumps to the original launcher. |
| **MiMo Code: child sessions are background-only** | MiMo Code shares the same `@mimo-ai/plugin` SDK as opencode. When MiMo Code emits `session.created` with `event.properties.info.parentID`, Clawd treats that child/subtask as headless background work owned by the root session. It is hidden from HUD/focus surfaces and does not contribute to multi-session fanout animations. |
| **MiMo Code: terminal focus limited to spawning terminal** | The plugin runs in-process with MiMo Code, so `source_pid` points to the terminal that launched MiMo Code. If you attach from a different window, terminal focus jumps to the original launcher. |
| **Orca: terminal focus is not supported on Linux** | Orca hosts its terminals in a detached `orca-terminal-daemon` whose own parent has already exited, so `Orca.exe` never appears in the agent's process tree and no window title carries the project path — neither of Clawd's usual strategies can find it. Focus instead uses `ORCA_PANE_KEY` from the environment plus Orca's own CLI (`orca terminal switch`), and requires the `orca` CLI: `PATH` first, then `%LOCALAPPDATA%\Programs\orca` on Windows and `/usr/local/bin/orca` or `~/.local/bin/orca` on macOS, because an app launched from Finder inherits none of the shell's `PATH`. Windows raises the window from the focus script; macOS activates the `Orca.app` bundle by absolute path (`/Applications` then `~/Applications`) after the pane switch succeeds, and reports `orca-app-not-found` if it is installed anywhere else. **Linux is unsupported**: the only by-name handle is WM_CLASS `orca`, which is a substring match that also hits GNOME's Orca screen reader and OrcaSlicer, so a miss would activate an unrelated window and report success. There, an Orca-hosted session falls back to the normal process-tree behavior, which cannot resolve the daemon. |
| **Orca: a terminal that advertises nothing can be mistaken for the pane** | The pane key is trusted only when Orca is the innermost terminal, which is decided from environment markers (`WT_SESSION`, `ConEmuPID`, `KONSOLE_VERSION`, the multiplexers `TMUX` / `STY` / `ZELLIJ`, and others). A terminal that sets no marker of its own — a bare `conhost` or `pwsh` window — started *from* an Orca pane inherits `TERM_PROGRAM=Orca` and the pane key, so Clawd raises Orca and reports a successful focus while the window the agent really lives in is never found. |
| **Orca on Windows: the first focus of a session can land on the wrong tab** | The window raise runs inside the generated focus script and is immediate, but the pane switch needs an `orca` CLI round-trip, and the first focus for a session pays a cold `terminal list` before its `terminal switch`. A cold CLI has been measured exceeding the 6 s timeout: the call is then killed (`orca-cli-timeout` in `focus-debug.log`) with Orca already in front, showing whichever tab was last active, and no switch happens at all. Clicking again works — the second attempt meets a warm CLI, and once the handle is cached the steady state is ~0.5 s. |
| **Orca on macOS: nothing comes forward when the pane is gone** | The generic macOS raise is suppressed for an Orca-hosted session, because it derives its target from the daemon's process path and would activate `Orca.app` before the pane switch has said which tab — or whether the pane still exists. `open` also *launches* Orca, and the terminal daemon outlives its window, so a session whose window has been closed would cold-start the IDE on a click. The pane switch therefore owns the raise, and if it fails nothing is activated at all: clicking the pet appears to do nothing, with the reason recorded in `focus-debug.log`. |
| **Orca: two or more Orca windows cannot be told apart** | The entire window title is `Orca`, with no project path to match on, so with more than one window open Clawd refuses to guess and raises nothing (`orca-window-ambiguous` in `focus-debug.log`). The tab switch still runs, so the correct pane comes forward inside a window that stays behind. Use a single Orca window for reliable click-to-focus. |
| **Orca on macOS: CLI lookup includes Homebrew and the app bundle** | In addition to `PATH`, `/usr/local/bin/orca`, and `~/.local/bin/orca`, Clawd checks Apple Silicon Homebrew at `/opt/homebrew/bin/orca` and the CLI bundled under `/Applications/Orca.app` or `~/Applications/Orca.app`. This is required for Finder-launched Clawd instances whose inherited `PATH` omits Homebrew. |
| **Orca over Remote SSH: pane focus only** | When Orca forwards a valid `ORCA_PANE_KEY` into its managed SSH PTY, Clawd accepts it only from hooks carrying both secure Remote SSH markers (`CLAWD_REMOTE=1` and `CLAWD_SSH_REMOTE=1`). Dashboard clicks and permission-card terminal jumps can then request the originating local Orca pane on Windows/macOS without treating the remote process PID as local; the Session HUD remains local-only. Clawd can obtain only the Orca CLI acknowledgement, not proof that the visible UI switched. In an Orca 1.4.161 same-machine Remote SSH loopback test, the CLI returned success but the visible UI did not switch to the remote worktree, so Remote SSH visual switching is not fully verified. Other remote terminals remain unfocusable, Linux remains unsupported, and Telegram Direct Send remains limited to local sessions. |
| **Pi: state-only integration** | Clawd observes Pi interactive-session lifecycle and tool events through a global extension, but does not intercept permissions or add confirmation prompts. Pi keeps its default YOLO execution behavior. |
| **Pi: session reload may briefly flicker** | Pi emits `session_shutdown` during reload/session replacement, then `session_start` for the new runtime. Clawd may briefly remove and recreate the Pi session. |
| **OpenClaw: state-only local TUI support** | Phase 1 observes OpenClaw plugin lifecycle/tool events for `openclaw tui --local`. It does not provide permission bubbles or terminal focus, and gateway/daemon/messaging deployments may not anchor to a local terminal window. |
| **OpenClaw: JSON5 config is not edited at startup** | OpenClaw accepts JSON5 and include-based config. Clawd startup sync edits only an existing strict JSON `~/.openclaw/openclaw.json`; JSON5/include configs are skipped unless you run the manual installer so OpenClaw's CLI can own the write. |
| **OpenClaw on Windows: native codex relay may fail** | If OpenClaw stalls or reports an unsafe native hook relay bridge when using its native `agentRuntime: codex` path, switch OpenClaw to an OpenAI-compatible model/provider such as `openai-codex/gpt-5.5`. This is OpenClaw-side behavior; Clawd only observes plugin state events and cannot repair the relay. |
| **CodeWhale: global session id cache** | Phase 1 keeps the last CodeWhale session id in a single file under `os.tmpdir()`. Running multiple CodeWhale instances concurrently can overwrite or clear that cache across instances, which may cross-wire state updates or create duplicate HUD labels. |
| **Qoder: state-only integration** | Phase 1 observes Qoder hook events via `~/.qoder/settings.json` for state and sessions. `PermissionRequest` / `PermissionDenied` are surfaced as passive notifications only — the hook always returns `{}` and never answers permission decisions, so every Allow / Deny choice stays in Qoder's native flow, with no Clawd permission bubbles. Startup recovery watches only the Qoder CLI processes (`qodercli` / `qoder-cli`), so an already-open idle Qoder IDE is not treated as active agent work. A real QoderWork IDE smoke is still pending and must not be inferred from Qoder CLI validation. |
| **Windows Terminal: tab focus is limited** | Windows Terminal exposes one host window/process for multiple tabs, so Clawd cannot reliably activate a specific tab. HUD/Dashboard focus works best with separate classic `cmd.exe`/PowerShell windows, or with separate Windows Terminal windows whose title contains the project folder name. On Windows 11, `cmd.exe` and PowerShell may be hosted by Windows Terminal unless the default terminal application is set to Windows Console Host. **v0.12.0 and earlier only**: when Windows Terminal is the OS default terminal app, every prompt submission also briefly flashed a console window (#627) — WT's console delegation doesn't always honor `CREATE_NO_WINDOW` on the hook's PowerShell snapshot, and switching the default terminal app to Windows Console Host was the workaround for that too. **v0.13.0** samples the foreground window from Clawd's own process instead (no subprocess spawn on that path), so the flash is fixed and this workaround is no longer needed there. |
| **Windows: hook process metadata needs Clawd running** | Terminal focus and session PIDs come from a process-tree lookup that the hook only performs while Clawd is actually running. From **v0.13.0**, after you quit Clawd, a leftover CLI hook no longer inspects the process tree at all — it posts what it has and stops. The visible effect is that a session started while Clawd was closed has no click-to-focus target until its next event with Clawd running; a session Clawd already knows keeps the PID it learned. The same applies for a few seconds after Clawd is force-killed, and whenever `~/.clawd/runtime.json` is unreadable (Doctor → Local server warns). Until you restart Clawd once on v0.13.0, the pre-v0.13.0 `runtime.json` has no owner field, so hooks treat Clawd as offline and omit this metadata — a single restart fixes it. |
| **Windows: some agents still run a PowerShell process lookup while Clawd is online** | The lookup above is still a hidden PowerShell that reads the process list, and security software may flag it. **v0.13.0** removes it when Clawd is not running, and no longer stores the agent's command line in the temporary cache (only a `headless` yes/no). The online path is unchanged for now — tracked in [#681](https://github.com/rullerzhou-afk/clawd-on-desk/issues/681), [#627](https://github.com/rullerzhou-afk/clawd-on-desk/issues/627) and [#634](https://github.com/rullerzhou-afk/clawd-on-desk/issues/634). |
| **macOS/Linux packaged auto-update** | DMG/AppImage/deb installs cannot auto-update — use `git clone` + `npm start` for auto-update via `git pull`, or download new versions manually from GitHub Releases. |
| **Linux/Wayland: limited dragging & cursor tracking** | Native Wayland forbids client-side window positioning and global cursor queries, so under a Wayland session the pet spawns centered, can't be dragged, and has no mouse tracking. On a Wayland session with an X server available, Clawd relaunches itself once under XWayland (`--ozone-platform=x11`) — Electron fixes the Ozone backend in C++ before any app code runs, so an in-process switch is too late — which restores window positioning and dragging; cursor tracking is then limited to the pet's own surfaces. Full-screen cursor tracking is **not** achievable under Wayland for an ordinary app — use a native X11 (Xorg) login session for that. `CLAWD_OZONE_PLATFORM` controls the automatic relaunch: `x11` forces the XWayland relaunch, `wayland`/`auto` keep the native-Wayland default; an explicit `--ozone-platform=…` you pass on the command line is always honored as-is. See [#441](https://github.com/rullerzhou-afk/clawd-on-desk/issues/441). |
| **No test framework for Electron** | Unit tests cover agents and log polling, but the Electron main process (state machine, windows, tray) has no automated tests. |
| **Claude Code: tools rejected when Clawd is offline** | When Clawd's HTTP server isn't running, the `PermissionRequest` hook (registered by Clawd) fails with `ECONNREFUSED`, and Claude Code currently denies the tool call instead of falling through to its built-in prompt — affecting `Edit`, `Write`, `Bash`, etc. This contradicts CC's documented non-blocking behavior for HTTP hook failures — see [anthropics/claude-code#46193](https://github.com/anthropics/claude-code/issues/46193). Workaround: keep Clawd running (recommended), or temporarily rename the `PermissionRequest` key in `~/.claude/settings.json` to disable the hook. |
| **Claude Code + CC Switch: protected auto-repair pause** | Clawd normally re-registers Claude hooks when another tool rewrites `~/.claude/settings.json`. If the file suddenly shrinks enough to look unsafe, Clawd pauses automatic repair to avoid preserving a partially rewritten config and Doctor reports Claude Code as needing Fix. Use **Settings -> Doctor -> Fix**, restart Clawd, or re-enable automatic Claude hook management to repair. CC Switch's Shared Config Snippet can carry Clawd hooks on the same machine, but those hooks include local paths and ports, so do not treat them as a cross-device snippet. |
